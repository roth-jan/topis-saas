# Wege-System TOPIS — ehrliche Übersicht (Stand 2026-05-29)

Aus dem Code rausgelesen, nicht aus dem Bauch. Wo ich Verständnis-Lücken sehe, steht das explizit dabei.

## 1. Was es überhaupt für „Pfad-artige" Konstrukte gibt

| Konstrukt | Datenstruktur | Wer erzeugt | Wozu | Im Store |
|-----------|---------------|-------------|------|---------|
| **Gang** | `Gang { points[], breite }` | Berater (Gang-Werkzeug) oder Auto-Generator | Mittellinien-Netz für A*-Routing | `gaenge[]` |
| **PathArea** | `PathArea { x, y, w, h }` | Layout-Import oder Berater (Wegfläche-Werkzeug) | Lastenheft 3.1.4.1: definiert „hier dürfen Wege liegen" | `pathAreas[]` |
| **Path** | `Path { waypoints[], startObjectId?, endObjectId?, autoGenerated? }` | Pfad-Werkzeug ODER WegeberechnungDialog | Persistente Wege im Layout | `paths[]` |
| **CockpitRoute** | `{ startId, endId }` | Cockpit-Tab Dropdown | Visuelles Spielzeug für Demo | `cockpitRoute` |
| **SimAuftrag** | `{ vonObjectId, nachObjectId, colli }` | Auftrag-Werkzeug ODER Volumen-Import | Logistik-Aufträge mit eigenem A*-Render | `simAuftraege[]` |
| **Distanzmatrix** | gemessene Distanzpaare | Excel-Import | „echte" Verteilweg-Werte (überschreibt A*) | `betriebsdaten-store` |

**Wichtig:** Path und SimAuftrag/CockpitRoute leben getrennt. Ein Path persistiert; ein SimAuftrag generiert beim Rendern frisch via A*. Sie wissen nichts voneinander.

## 2. Wer triggert was

### Object verschoben/skaliert (`updateObject`)
- Wenn x/y/w/h geändert → `scheduleRecomputeForObject(id)` → 80ms Debounce → `recomputeAllPaths()`
- `recomputeAllPaths` läuft über **alle Paths mit `startObjectId + endObjectId`**, ruft A* neu auf, ersetzt Waypoints
- **Manuelle Paths ohne Anker** bleiben unverändert (gewollt laut Code-Kommentar)
- **SimAuftraege werden NICHT recomputed** durch Object-Move — sie rendern aber jedesmal frisch beim Canvas-Draw, also ist das transparent

### Object gelöscht (`deleteObject`)
- Paths mit `startObjectId === id || endObjectId === id` bekommen Präfix `⚠ ` im Namen, bleiben aber als „Geister-Geometrie" im Layout
- SimAuftraege mit diesem Object werden komplett gelöscht
- **Inkonsistenz:** Paths verwaisen sanft, SimAuftraege hart. Begründung im Code: „User-Arbeit nicht zerstören"

### Gang geändert/gelöscht (`setGaenge`, `updateGang`, `deleteGang`)
- Triggert ebenfalls `scheduleRecomputeForObject(-1)` → alle Pfade neu
- Konsequenz: Topologie-Änderung am Gang-Netz aktualisiert alle Auto-Pfade

### Pfad-Werkzeug klickt (manueller Pfad)
- **Klick 1**: Hinweis-Toast, Waypoint gesetzt
- **Klick 2** wenn beide Endpunkte auf einem Anker (Tor/Bereich/Stellplatz) → SOFORT A*-Route über Gänge + Save. Keine Luftlinien-Wand-Validation.
- **Klick 2 ohne Anker-Anker-Konstellation**: Luftlinien-Wand-Check, wenn OK → Waypoint hinzu
- **Klick 3+**: weiterer Waypoint
- **Enter**: Save (für 3+ Klick-Pfade oder freie Skizzen)
- **ESC**: Abbruch

### WegeberechnungDialog (Massen-Auto-Wege)
- Alle Tor × (Tor+Bereich+Stellplatz) — A* über Gang-Netz
- Speichert mit `autoGenerated: true` als Path-Objekte
- `deleteAutoGeneratedPaths()` räumt sie wieder ab

## 3. Wo Validation greift (manuelle Pfade)

| Stelle | Was wird geprüft | Greift bei |
|--------|------------------|-----------|
| Klick-Handler `tool==='path'` | pathArea-Containment (wenn pathAreas existieren) | jedem Klick |
| Klick-Handler `tool==='path'` | `lineCrossesAnyWall(letzter, neuer Klick)` | Klick 2+, NICHT bei Anker-Anker-Auto-Route |
| `savePathWithLinks` | A* findet keinen Weg → Toast „kein durchgehender Weg" | nur bei 2-Klick-Anker-Routing |
| `recomputeAllPaths` | wenn A* fehlschlägt → alter Pfad bleibt erhalten | beim Auto-Update |

## 4. Was ich verstehe und wo ich Lücken sehe

**Klar verstanden:**
- Die Datenstrukturen oben
- Klick→Pfad-Werkzeug-Flow inkl. der heute eingebauten Auto-Route bei 2 Ankern
- Auto-Update bei Object-Move (recomputeAllPaths + Debounce)
- Verwaisten-Logik bei Object-Löschung
- A* in `findPathBetweenObjects` arbeitet auf dem **Gang-Graph**, nicht auf den pathAreas
- `lineCrossesAnyWall` mit Türen als Durchlass

**Architektur-Inkonsistenz die ich sehe und Klarstellung braucht:**

1. **pathArea vs. Gang**: pathAreas sind reine Visual + Klick-Constraints. A* nutzt nur die Gang-Mittellinien. Wenn die Gang-Linien NICHT innerhalb pathAreas verlaufen, gibt's Diskrepanz: User darf hier nicht klicken, aber A* routet doch da entlang. Frage: sollten Gänge automatisch innerhalb pathAreas sein? Oder andersherum: sollte das Pfad-Werkzeug auf Gang-Linien snappen statt auf pathAreas?

2. **SimAuftrag vs. Path**: gleiches A*, aber separate Lebenszyklen. Beim Verschieben eines Tors wird der Path neu berechnet, der SimAuftrag-Render-Pfad auch — aber die SimAuftrag-Distanz wird NICHT gespeichert. Verteilweg-Pipeline rechnet eigenständig.

3. **Verteilweg-Pipeline kennt manuelle Paths nicht**: `verteilweg-rechner.ts` arbeitet auf Scandaten + A* (oder Distanzmatrix). Manuell gezeichnete Paths fließen NICHT in den Verteilweg ein. Das könnte unter „IST-Weg dokumentieren" relevant sein.

4. **CockpitRoute und Path teilen sich keinen State**: Cockpit zeigt eine A*-Route on-the-fly, persistiert sie aber nicht als Path. Wenn der User die Route „behalten" will, muss sie manuell als Path nachgezeichnet werden.

**Was ich nicht im Detail im Kopf habe:**

- Die genaue A*-Heuristik in `findPathBetweenObjects` — insbesondere die „Anbindungs-Logik" für Tor → erster Gang-Knoten (gestrichelte Linie in der Visualisierung). Müsste ich `pathfinding.ts:findPathBetweenObjects` nochmal komplett lesen.
- Die FFZ-Mindestbreite-Logik in `buildGangGraph` — Filter, ob Gänge schmal sind für ein bestimmtes Flurförderzeug
- `verteilweg-rechner.ts` — wie genau die Pipeline aus Scandaten + A* + Colli-Gewichtung den Wert berechnet
- WegeberechnungDialog: Bedingungen für Pfad-Validität (woher das ⚠-Symbol kommt das wir gestern gesehen haben — alle 102 Pfade mit ⚠)

**Architektur-Brocken die im Lastenheft fehlen aber faktisch im Code sind:**
- CockpitRoute (Spielerei)
- SimAuftrag (Fahrplan-Simulation)
- Distanzmatrix (überschreibt A*-Werte)
